# 8섹션 GDD 표준

> 모든 시스템 단위 GDD 는 다음 8개 섹션을 정해진 순서로 포함한다.
> 누락 = "구조적 미완성" 으로 간주되어 검토에서 차단된다.

## 핵심 원리

GDD 는 "한 번 보고도 다른 디자이너가 같은 그림을 그릴 수 있는가" 가 통과 기준이다.
8섹션은 그 기준을 **체크 가능한 형태**로 분해한 것이다.

각 섹션은 다른 섹션이 답하지 않는 고유 질문을 답한다:

| 섹션 | 답하는 질문 |
|---|---|
| 1. Overview | 이 시스템이 뭐고, 한 문장으로 무엇을 하는가? |
| 2. Player Fantasy | 플레이어는 이걸 통해 *무엇이 된* 느낌을 받는가? |
| 3. Detailed Rules | 모호함 없이, 정확히 어떻게 작동하는가? |
| 4. Formulas | 모든 수치 계산이 변수·범위·예시와 함께 정의됐는가? |
| 5. Edge Cases | 예외 상황에서 어떻게 동작하는가? (명시적으로) |
| 6. Dependencies | 어떤 시스템과 어떻게 연결되는가? (양방향) |
| 7. Tuning Knobs | 어떤 값을 안전하게 조정할 수 있는가? (범위와 함께) |
| 8. Acceptance Criteria | 이게 작동한다는 걸 어떻게 증명하는가? |

---

## 섹션별 작성 표준

### 1. Overview (개요)

**길이**: 1 문단 (3~5 줄)

**포함**:
- 시스템의 한 줄 정의
- 게임에서의 역할 (어떤 플레이어 경험을 만드는가)
- 핵심 입력·출력 (개념 수준)

**예시 (낚시 미니게임)**:
> 두더지잡기식 캐치 메커니즘. 화면에 등장하는 오브젝트를 마우스 클릭으로 잡으면 점수 획득.
> "읽고 결단하라" 기둥의 코어 메카닉.
> 입력: 사용자 클릭 → 출력: 캐치 성공/실패 이벤트, 점수.

**금지**:
- 마케팅 문구 ("재미있는", "혁신적인")
- 미정 사항 표시 ("TBD", "추후 결정")
- 다른 섹션에서 다룰 내용 (룰, 공식 등)

---

### 2. Player Fantasy (플레이어 판타지)

**길이**: 3~5 줄

**포함**:
- 플레이어가 *무엇이 된* 느낌인지 (역할/존재)
- 그 순간의 핵심 감정 (1~3 단어)
- 그 감정이 어느 메카닉에서 발생하는지

**예시**:
> 플레이어는 **순간의 판단으로 가치를 결정짓는 사냥꾼**이 된다.
> 핵심 감정: 긴장 → 집중 → 쾌감.
> 화면에 6개 오브젝트가 동시에 움직일 때 "어느 걸 잡을지" 0.5초 내 결정해야 하는 순간이 정점.

**금지**:
- "재미있는 느낌" — 너무 추상적
- 시스템 작동 설명 (룰 섹션의 영역)
- 메카닉 없는 감정 ("비장함" 인데 메카닉적 근거 없음)

---

### 3. Detailed Rules (상세 규칙)

**길이**: 시스템 복잡도에 비례, 보통 1~3 페이지

**포함**:
- 번호 매긴 룰 5~15개
- 각 룰은 단일 책임 (한 룰이 두 가지 말하지 않음)
- 룰 간 우선순위 명시 (충돌 시 어느 게 우선인가)

**작성 양식**:
```
R-1: 활성 오브젝트 동시 표시 수 = SpawnConfig.max_active (기본 6)
R-2: 클릭은 가장 최근에 등장한 오브젝트에 우선 적용. 동률 시 화면 좌상단 우선.
R-3: 클릭 정확도는 오브젝트 히트박스 내부일 때만 인정. 가장자리 ±2px 허용.
R-4: 오브젝트 사라짐 = 수명 만료 또는 클릭 성공. 둘 다 카운트는 1회.
```

**금지**:
- "적절히", "필요 시", "일반적으로" — 모호함
- 한 룰에 여러 조건 ("R-X: A 일 때 B 하고, C 일 때 D 한다") → 분리

---

### 4. Formulas (공식)

**포함** (모든 공식마다):
- 변수 정의표 (이름·의미·타입·단위)
- 공식 본체 (수학 표기 또는 의사코드)
- 변수 예상 범위
- 예시 계산 1~2개

**작성 양식**:
```
점수 공식: Score = BaseValue × ComboMultiplier × DifficultyBonus

| 변수 | 의미 | 타입 | 범위 |
|------|------|------|------|
| BaseValue | 오브젝트 기본 점수 | int | [10, 1000] |
| ComboMultiplier | 콤보 배율 | float | [1.0, 5.0] |
| DifficultyBonus | 난이도 보너스 | float | [1.0, 3.0] |

예시:
- 일반 오브젝트 (BaseValue=100), 콤보 3 (Multiplier=1.5), 보통 난이도 (Bonus=1.0)
  → Score = 100 × 1.5 × 1.0 = 150
- LEGENDARY 오브젝트 (BaseValue=1000), 콤보 10 (Multiplier=5.0), 하드 (Bonus=2.0)
  → Score = 1000 × 5.0 × 2.0 = 10,000
```

**금지**:
- 변수 없는 공식
- 범위 없는 변수 ("적당한 값")
- 예시 없는 복잡한 공식

### 5. Edge Cases (엣지 케이스)

**최소 5개 명시**

**포함** (각 케이스):
- 상황 (1줄, 구체적)
- 동작 (정확히 어떻게 처리되는지)
- 사용자 피드백 (어떻게 보이는지)

**작성 양식**:
```
EC-1: 클릭이 두 오브젝트의 히트박스에 동시 들어감
     → R-2 의 룰 적용 (최근 등장 우선). 다른 오브젝트는 미반응.
     → UI: 잡힌 오브젝트만 캐치 이펙트 재생.

EC-2: 일시정지 중 오브젝트 수명 타이머 처리
     → 타이머 일시정지. 재개 시 정확히 멈춘 시점부터 진행.

EC-3: 마지막 1초에 오브젝트 등장
     → 등장 거부 (남은 시간 < 오브젝트 최소 수명일 때 스폰 차단).
```

**금지**:
- "적절히 처리한다" — 무엇이 적절한지 명시
- "예외 발생" — 어떤 예외인지, 사용자에게 어떻게 보이는지

---

### 6. Dependencies (의존성)

**포함**:
- **상위 의존** (이 시스템이 사용하는 것들): 시스템명 + 호출/구독하는 인터페이스
- **하위 의존** (이 시스템을 사용하는 것들): 시스템명 + 노출하는 이벤트/API
- **양방향성 검증**: 상대 GDD 도 이 관계를 명시해야 함 (없으면 stale)

**작성 양식**:
```
상위 의존:
- 입력 핸들러: 마우스 클릭 위치 수신 (`mouse_clicked(position)`)
- 오브젝트 스포너: 활성 오브젝트 리스트 조회 (`get_active_objects()`)
- 런 매니저: 일시정지 신호 구독 (`paused`/`resumed`)

하위 의존:
- 스코어링 시스템: 캐치 성공 이벤트 발행 (`object_caught(id, value)`)
- HUD: 캐치 카운트 변경 알림 (`catch_count_changed(count)`)
```

**금지**:
- 한 줄로만 ("스코어링과 연결됨") → 어떤 인터페이스인지 명시
- 의존하는 쪽에만 적고 받는 쪽 GDD 에 미반영

---

### 7. Tuning Knobs (튜닝 노브)

**포함** (각 노브):
- 변수명 (코드/리소스의 정확한 이름)
- 의미 (1줄)
- 안전 범위 (min ~ max)
- 권장값
- 변경 시 영향 (어느 게임 느낌에 영향)

**작성 양식**:
```
| 노브 | 의미 | 안전 범위 | 권장값 | 영향 |
|------|------|----------|--------|------|
| max_active_objects | 동시 활성 오브젝트 수 | 3 ~ 10 | 6 | 인지 부하 |
| object_lifetime_ms | 오브젝트 수명 | 800 ~ 3000 | 1500 | 긴장감 |
| spawn_interval_ms | 스폰 간격 | 200 ~ 1500 | 700 | 페이스 |
```

**금지**:
- 범위 없는 노브 ("적당히 조정")
- 한 노브가 다른 노브와 강한 결합 ("X 와 Y 는 같이 조정해야 함") 명시 누락

---

### 8. Acceptance Criteria (인수 기준)

**최소 5개**

**포함** (각 AC):
- 테스트 가능한 조건 (관찰 가능한 결과)
- 통과 기준 (구체적 수치 또는 boolean)

**작성 양식**:
```
AC-1: 60fps 환경에서 클릭 → 시각 피드백 지연 < 100ms (3 frames)
AC-2: 동시 활성 오브젝트 6개 상태에서 클릭 정확도 95% 이상 (히트박스 내부 클릭의 95%가 인정됨)
AC-3: 일시정지 후 재개 시 모든 오브젝트의 잔여 수명이 정확히 보존됨 (±50ms 오차)
AC-4: LEGENDARY 오브젝트 등장 시 BGM duck 효과 0.3초 내 적용
AC-5: 60초 플레이세션에서 메모리 누수 없음 (시작 ↔ 종료 메모리 차이 < 5MB)
```

**금지**:
- 주관적 평가 ("재미있어야 한다", "느낌이 좋아야 한다") → Game Feel 명세로 분리
- 측정 불가능한 기준 ("매끄러운 동작") → 구체적 수치
- 환경 명시 안 함 (60fps? 30fps? 어떤 하드웨어?)

## 검증 체크리스트

GDD 작성 후 다음을 자기 점검:

- [ ] 8개 섹션 모두 존재
- [ ] 1~2 의 한 줄 요약을 다른 사람에게 읽어주면 그게 어떤 게임의 시스템인지 짐작 가능
- [ ] 룰 (3) 만 보고도 시스템을 시뮬레이션 가능
- [ ] 공식 (4) 의 모든 변수가 정의됐고 범위가 있음
- [ ] 엣지 케이스 (5) 최소 5개, 각각 명시적 처리
- [ ] 의존성 (6) 이 양방향 일치 (상대 GDD 도 확인)
- [ ] 튜닝 노브 (7) 모두 안전 범위 명시
- [ ] AC (8) 모두 측정 가능, 환경 명시
