# Cross-GDD 일관성 검증 패턴

> 각 GDD 가 *내부적으로* 완성되어도, *서로* 모순되면 게임이 깨진다.
> 모든 GDD 작성 후 cross-review 단계에서 다음 패턴들을 검증한다.

## 핵심 원리

단일 GDD 검증 (`/design-review`) 이 *각 시스템 내부 무결성* 을 본다면, cross-review 는 *시스템 간 정합성* 을 본다.

검증 대상은 9 개 카테고리:

| # | 카테고리 | 영향 |
|---|---------|------|
| 1 | 의존성 양방향 | 🔴 BLOCKING |
| 2 | 룰 충돌 | 🔴 BLOCKING |
| 3 | 소유권 충돌 | 🔴 BLOCKING |
| 4 | 공식 범위 불일치 | 🟡 WARNING |
| 5 | Stale 참조 | 🟡 WARNING |
| 6 | 인수 기준 cross-check | 🟡 WARNING |
| 7 | 기둥 정렬 drift | 🟡 WARNING |
| 8 | 인지 부하 누적 | 🟢 INFO |
| 9 | 지배 전략 | 🟢 INFO |

---

## 1. 의존성 양방향 (BLOCKING)

별 문서 `bidirectional-dependency.md` 의 양방향 검증을 cross-review 시 실행.

```
미니게임 → 스코어링 (상위 의존)
       ↔
스코어링 → 미니게임 (하위 의존, 양방향 일치 확인)
```

미일치 시: BLOCKING. 어느 쪽이 옳은지 결정 후 다른 쪽 수정.

---

## 2. 룰 충돌 (BLOCKING)

서로 다른 GDD 가 동일 상황에 대해 다른 룰을 명시.

### 예시

```
미니게임 GDD R-3:
  "오브젝트 클릭 정확도는 히트박스 내부일 때만 인정. 가장자리 ±2px 허용."

입력 핸들러 GDD R-1:
  "마우스 클릭의 픽셀 정확도는 ±5px 까지 허용 (모니터 DPI 보정)."
```

→ 가장자리 클릭이 인정되어야 하나? 미니게임은 ±2, 입력은 ±5.

### 검증 절차

1. 모든 GDD 의 룰 (R-N) 추출
2. 동일 도메인 (입력 처리, 점수 계산, 시간 처리 등) 의 룰 묶음
3. 묶음 내 모순 검색

### 해결

- 어느 쪽이 옳은지 결정 (보통 더 *세밀한 시스템* 우선)
- 양 GDD 동시 수정
- 변경 사유 기록 (혹은 ADR)

---

## 3. 소유권 충돌 (BLOCKING)

두 시스템이 같은 책임을 주장.

### 예시

```
런 매니저 GDD: "런 종료 시 최종 점수를 결과 화면에 전달"
스코어링 시스템 GDD: "런 종료 시 점수 집계 + 결과 화면 트리거"
```

→ 누가 결과 화면 트리거? 둘 다 한다고 주장.

### 검증 절차

1. 각 GDD 의 "책임" 또는 Overview 섹션 추출
2. 동일 동작에 대한 다중 소유 검색
3. "X 가 Y 를 한다" 식 진술 비교

### 해결

- 단일 책임 원칙 적용. 한 동작 = 한 시스템.
- 소유자 결정 (보통 *더 상위 레이어*가 트리거 발행, *전문 시스템*이 처리)
- 양 GDD 동시 수정 (소유자 명시 + 비소유자 책임 제거)

## 4. 공식 범위 불일치 (WARNING)

시스템 A 의 출력 범위가 시스템 B 의 입력 기대 범위에 안 맞음.

### 예시

```
스코어링 시스템 공식:
  Score = BaseValue × Combo × Bonus
  BaseValue ∈ [10, 1000]
  Combo ∈ [1, 99]
  Bonus ∈ [1.0, 3.0]
  → Score ∈ [10, 297000]

HUD 시스템 점수 표시:
  6자리 숫자 표시 (000000 ~ 999999)
  → 입력 기대 ∈ [0, 999999]
```

→ Score 가 297000 까지인데 HUD 는 999999 까지 표시 가능. 표시 자릿수 낭비. 또는 반대로 Score 최댓값이 HUD 표시 한계 초과 → 자릿수 부족.

### 검증 절차

1. 모든 GDD 의 공식 출력 범위 추출
2. 그 출력을 받는 시스템의 입력 기대 추출
3. 범위 불일치 검색

### 해결

- 공식 범위와 표시 범위 정렬
- 또는 클램핑·스케일링 명시

## 5. Stale 참조 (WARNING)

GDD 가 더 이상 존재하지 않는 시스템·룰·이벤트를 참조.

### 예시

```
미니게임 GDD: "오브젝트 매니저(ObjectManager) 의 get_active() 호출"

(실제로는 시스템 이름이 "오브젝트 스포너(ObjectSpawner)" 로 변경됨)
```

→ 이름 변경 시 모든 참조도 업데이트되어야 함.

### 검증 절차

1. 시스템 인덱스의 정식 이름 목록 확보
2. 각 GDD 에서 참조되는 시스템 이름 추출
3. 인덱스에 없는 이름 발견 시 stale

### 해결

- 정식 이름으로 일괄 치환
- 또는 인덱스에 별칭 등록 (가능 시)

---

## 6. 인수 기준 Cross-Check (WARNING)

각 GDD 의 AC 가 다른 시스템의 가정과 충돌.

### 예시

```
미니게임 GDD AC-1: "60fps 환경에서 클릭 → 시각 피드백 < 100ms (3 frames)"
입력 핸들러 GDD AC-2: "마우스 입력 폴링 간격 200ms"
```

→ 입력 폴링이 200ms 인데 미니게임은 100ms 내 피드백 요구. 불가능.

### 검증 절차

1. 모든 GDD 의 AC 추출
2. 의존 관계의 AC 들끼리 비교
3. 한 시스템의 AC 가 다른 시스템의 AC 로 달성 불가능하면 충돌

### 해결

- 더 엄격한 쪽이 옳음 (보통 사용자에 가까운 시스템)
- 의존 시스템의 AC 강화 (입력 폴링을 50ms 로)

---

## 7. 기둥 정렬 Drift (WARNING)

시스템들이 어느 기둥을 강화하는지 불균형.

### 예시

```
기둥 1 "읽고 결단하라": 시스템 A, B, C 가 강화
기둥 2 "뭐가 나올까": 시스템 D 만 강화
기둥 3 "짧고 굵게": 시스템 (없음)
```

→ 기둥 3 을 강화하는 시스템 부재. 기둥이 *말로만* 있고 메카닉 부재.

### 검증 절차

1. 각 GDD 의 "기둥 정렬" 항목 추출
2. 기둥별로 강화 시스템 카운트
3. 불균형 또는 부재 검색

### 해결

- 기둥 부재: 그 기둥을 강화하는 시스템 추가 또는 기둥 자체 재고
- 한 기둥 과대: 시스템 분해 또는 다른 기둥 보강

## 8. 인지 부하 누적 (INFO)

플레이 중 동시 활성화되는 시스템이 4개 초과.

### 예시

```
한 게임 화면에 동시 활성:
  1. 미니게임 (캐치 결정)
  2. 콤보 시스템 (콤보 유지)
  3. 난이도 디렉터 (스폰 변화)
  4. 스코어링 (점수 누적)
  5. 인벤토리 슬롯 (아이템 사용)
  6. 도감 인디케이터 (신규 발견)
```

→ 6개 동시 주의 = 인지 부하 한계 초과 (Miller's 7±2 위반).

### 검증 절차

1. "활성 화면" 별로 동시 활성 시스템 식별
2. 4 초과 시 INFO 로 플래그
3. 사용자 의도 vs 한계 검토

### 해결

- 일부 시스템 비주기 활성화 (콤보 인디케이터 → 콤보 ≥ 3 일 때만)
- 또는 시스템 통합 (스코어링 + 콤보 = 한 시스템)

---

## 9. 지배 전략 (INFO)

한 메카닉이 *너무 강해서* 다른 메카닉이 무의미해짐.

### 예시

```
스코어링 공식:
  - 일반 캐치: 100~500점
  - LEGENDARY 캐치: 5000~10000점
  - 콤보 보너스: ×1.0 ~ ×5.0
```

→ LEGENDARY 1번 = 일반 캐치 20번. 일반 캐치는 무가치, LEGENDARY 만 노리는 게 *지배 전략*. 다른 모든 결정 무의미해짐.

### 검증 절차

1. 모든 게임 결정의 *예상 보상* 계산
2. 한 결정이 다른 결정의 5배 이상이면 의심
3. 플레이어가 "한 가지만 하면 됨" 인지 확인

### 해결

- 보상 분포 평탄화 (LEGENDARY 보상 줄이기 또는 일반 캐치 가치 증가)
- 또는 명시적 페널티 (LEGENDARY 만 노리면 콤보 끊김 등)

---

## 검증 절차 (cross-review 워크플로우)

```
1. 모든 MVP GDD 가 개별 review APPROVED 상태
2. 모든 GDD 본문 수집
3. 9개 카테고리 순서대로 검증
4. 각 발견 사항 분류 (BLOCKING / WARNING / INFO)
5. 리포트 작성:
   - BLOCKING: 즉시 수정 필요
   - WARNING: 가능하면 수정, 미수정 사유 기록
   - INFO: 인지하고 진행
6. BLOCKING 0 + WARNING 결정됨 = cross-review PASS
```

---

## 안티패턴

### 1. 개별 review 만, cross-review 누락
각 GDD 는 완벽하지만 합쳐놓으면 모순.

해결: 모든 GDD 작성 완료 후 별 단계로 cross-review.

---

### 2. WARNING 무시
"INFO 만 있으니 OK" — 누적되면 큰 문제.

해결: WARNING 도 명시적 결정. "왜 이대로 두는가" 기록.

---

### 3. cross-review 를 한 번만
디자인 변경 시마다 재실행해야 함. 한 번 통과로 영구 안정 아님.

해결: 디자인 변경 propagation 시 cross-review 재실행.

---

## 검증 체크리스트

cross-review 시:

- [ ] 의존성 양방향 — 모든 쌍 일치
- [ ] 룰 충돌 — 동일 도메인 룰 모순 없음
- [ ] 소유권 충돌 — 단일 책임 위반 없음
- [ ] 공식 범위 — 출력 ↔ 입력 정렬
- [ ] Stale 참조 — 모든 시스템 이름이 인덱스에 존재
- [ ] AC cross-check — 의존 관계 AC 충돌 없음
- [ ] 기둥 정렬 — 모든 기둥이 최소 1 시스템 강화
- [ ] 인지 부하 — 동시 활성 ≤ 4 (이상 시 명시적 결정)
- [ ] 지배 전략 — 보상 분포 5배 이내 (이상 시 명시적 결정)
- [ ] 리포트 작성 + 분류 + 사용자 결정 기록
