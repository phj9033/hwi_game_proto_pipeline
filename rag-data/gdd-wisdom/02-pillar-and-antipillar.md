# 게임 기둥과 안티 기둥

> 기둥은 "이 게임이 *반드시 되어야 할 것*", 안티 기둥은 "이 게임이 *절대 되지 말아야 할 것*".
> 둘 다 명시되어야 디자인 결정의 흐려짐(drift)을 막을 수 있다.

## 핵심 원리

게임 디자인은 결정의 연속이다. 매 결정마다 "이 게임답냐"를 판단하려면 기준이 필요하다.
기둥 3개와 안티 기둥 3개는 그 기준의 핵심이다.

**기둥**: 디자인 결정에서 "예" 라고 답하는 방향
**안티 기둥**: 디자인 결정에서 "아니오" 라고 답하는 방향

둘 모두 단순히 슬로건이 아니라 **메카닉적 함의**를 가져야 한다 — 추상적 단어로 끝나면 운영 불가.

---

## 기둥 (Pillars)

### 형식

기둥 1개는 다음 3요소로 구성:

```
1. 슬로건 (한 문장, 인상적, 외울 수 있는)
2. 메카닉 함의 (이 기둥이 어떤 메카닉으로 구현되는가)
3. 측정 가능한 신호 (이 기둥이 잘 구현됐는지 판별하는 기준)
```

### 예시 (Reel Odyssey, 낚시 아케이드 게임)

**기둥 1: "읽고 결단하라"**
- 슬로건: 매 캐치는 판단의 순간이다.
- 메카닉 함의: 화면에 동시 표시되는 오브젝트 수가 충분히 많아 "어느 걸 잡을지" 0.5초 내 결정해야 함. 점수·희귀도가 시각적으로 즉시 식별 가능.
- 측정 신호: 플레이어가 모든 오브젝트를 같은 가치로 대하지 않음. 의도적 선택의 흔적이 플레이 영상에 보임.

**기둥 2: "뭐가 나올까, 그리고 무엇이 될까"**
- 슬로건: 미스터리와 정체성.
- 메카닉 함의: 오브젝트 풀이 충분히 다양해서 매 등장이 "뭐가 나올지" 의 기대를 만듦. 잡은 것이 그 런(run) 동안 플레이어를 변화시킴.
- 측정 신호: 동일 컨셉 두 런이 다른 양상으로 흘러감. 플레이어가 "이번 런은 ~ 빌드" 라고 자기 식별 가능.

**기둥 3: "짧고 굵게"**
- 슬로건: 10~15분 완결 런.
- 메카닉 함의: 한 런이 명확한 시작·중간·끝을 가지며, 새 런 진입까지 3초 이내. 불필요한 메뉴 단계 없음.
- 측정 신호: 한 세션에 평균 3~5 런 가능. "한 판 더" 가 자연스러움.

### 기둥 작성 시 점검 질문

각 기둥마다 답할 수 있어야:

1. 이 기둥과 충돌하는 메카닉 결정이 닥쳤을 때, 어느 쪽으로 갈지 분명한가?
2. 이 기둥이 우리 게임에 *고유한가*? (다른 비교 게임도 이 기둥을 가지면 USP 가 약함)
3. 메카닉 함의가 코드 한 줄 수준까지 내려가는가? (그렇지 않으면 슬로건일 뿐)
4. 누군가 "이 기둥이 잘 구현됐냐?" 물으면 뭘 가리켜 답할 수 있는가?

## 안티 기둥 (Anti-Pillars)

### 왜 필요한가

기둥이 "예" 라면, 안티 기둥은 "아니오". 두 개 다 있어야 결정이 명확.
**스코프 폭주의 90% 는 안티 기둥 부재**에서 온다 — "그것도 좋겠다" 가 거절 기준 없이 누적됨.

### 형식

```
1. 거부 선언 (이 게임이 의도적으로 *되지 않을* 것)
2. 거부 이유 (왜 거부해야 우리 게임 정체성이 유지되는가)
3. 유혹 신호 (어떤 상황에서 우리가 이 안티 기둥을 어길 유혹을 받는가)
```

### 예시 (Reel Odyssey)

**안티 기둥 1: "복잡한 시뮬레이션이 되지 않는다"**
- 거부 선언: 낚시대 부품·미끼 종류·물고기 생태 시스템 도입 거부.
- 이유: 기둥 1·3 과 충돌. 즉각 결단·짧은 런 경험을 무겁게 만듦.
- 유혹 신호: "낚시 게임인데 미끼 시스템이 있어야 하지 않을까?" 라는 본능적 기대.

**안티 기둥 2: "스토리 캠페인이 되지 않는다"**
- 거부 선언: 일회성 스토리 모드, 보스전 캠페인, 대화 시스템 거부.
- 이유: 기둥 3 (짧고 굵게)·기둥 2 (런별 정체성) 와 충돌. 일회성 콘텐츠는 반복 가치를 죽임.
- 유혹 신호: "분위기 잡는 인트로 시퀀스만이라도..." 식의 슬그머니 추가.

**안티 기둥 3: "온라인·소셜 기능이 되지 않는다"**
- 거부 선언: 멀티플레이어, 친구 리더보드, 소셜 공유 거부.
- 이유: 솔로 개발 스코프 보호. 기둥 3 의 즉시성과 충돌.
- 유혹 신호: "리더보드만이라도..." → 백엔드·계정 시스템 줄줄이 따라옴.

## 기둥 ↔ 시스템 정렬 (Drift 감지)

### 시스템 GDD 작성 시

각 시스템이 어느 기둥을 *어떻게* 강화하는지 명시:

```markdown
## 코어 메카닉 (시스템: 두더지잡기 미니게임)

### 기둥 정렬
- 기둥 1 ("읽고 결단하라"): 동시 6개 오브젝트 + 0.7초 평균 수명 → 직접 구현
- 기둥 2 ("뭐가 나올까"): 오브젝트 풀 15종 + 가중치 랜덤 + pity 시스템 → 직접 구현
- 기둥 3 ("짧고 굵게"): 60초 런 + 3초 내 재시작 → 직접 구현
```

### Drift 신호

다음 중 하나라도 나타나면 기둥에서 멀어지는 중:

- 시스템이 어느 기둥에도 속하지 않음 → 스코프 외 기능
- 시스템이 기둥과 충돌 (느려지게 함, 복잡하게 함) → 안티 기둥에 가까움
- 기둥이 모호해서 "다 들어맞는다" 라고 답하게 됨 → 기둥이 너무 추상적
- 새 아이디어가 안티 기둥과 충돌하는데 "이건 예외" 라고 합리화

### Drift 발생 시 대응

1. **기둥을 강화**: 안티 기둥 추가, 기둥 슬로건 더 구체적으로
2. **시스템을 자르기**: 기둥에 안 맞으면 폐기 (Vertical Slice 이후로 미루기)
3. **기둥을 변경**: 마지막 수단. 변경하면 기존 모든 시스템 GDD 재정렬 필요

## 안티패턴

### 1. "재미있는 게임" 이라는 기둥
너무 일반적. 모든 게임의 목표라 거절 기준으로 쓸 수 없음.
→ 어떤 *종류의* 재미인지 한 단계 구체화.

### 2. 메카닉 함의 없는 기둥
"몰입감 있는 분위기" — 좋은데 어떤 메카닉으로?
→ "조명·사운드의 동기화로 BPM 60 근방에서 호흡 일치" 같은 구체화.

### 3. 안티 기둥 부재
기둥만 적고 안티 기둥 없음. 결정의 절반(거부)이 비어있음.
→ 가장 흔한 실수. 무조건 3개 안티 기둥 적기.

### 4. 안티 기둥 슬그머니 위반
"이건 예외, 한 번만" 식의 누적. 6개월 후 안티 기둥과 정반대 게임이 됨.
→ 안티 기둥 위반은 별 ADR 작성 필수. 가벼운 결정 금지.

### 5. 7개 기둥
3개도 많다. 4개 이상은 비중 분산되어 결정 가이드 역할 못함.
→ 정확히 3개. (5개 이상이면 우선순위가 없는 것)

## 기둥 검증 체크리스트

- [ ] 기둥 정확히 3개
- [ ] 안티 기둥 정확히 3개
- [ ] 각 기둥에 슬로건 + 메카닉 함의 + 측정 신호
- [ ] 각 안티 기둥에 거부 선언 + 이유 + 유혹 신호
- [ ] 모든 시스템 GDD 가 어느 기둥을 강화하는지 명시
- [ ] 안티 기둥 위반 시 ADR 통한 명시적 결정 절차 존재
