# GDD 안티패턴 모음

> 다음 패턴이 GDD 에 나타나면 즉시 차단·수정 대상.
> 8섹션별로 반복적으로 발생하는 실수들.

## 일반 안티패턴 (전 섹션 공통)

### A1. 정성 단어 의존

```
❌ "재미있는 액션", "독특한 메카닉", "몰입감 있는 분위기"
✅ "0.5초 내 결정해야 하는 6개 동시 표시", "10개 메카닉 풀 + 가중치 랜덤", "BPM 60 동기 조명·사운드"
```

문제: 측정 불가능. 검토자가 "이게 잘 됐는지" 판단 못함.

해결: 모든 정성 단어를 정량 또는 구체적 메카닉으로 환원.

---

### A2. TBD / 추후 결정 / 미정

```
❌ "스폰 간격: TBD", "이건 나중에 결정", "추후 협의 필요"
✅ "스폰 간격: 700ms (튜닝 범위 200~1500ms)" 또는 명시적 Open Question 섹션
```

문제: GDD 의 본질은 *결정* 의 기록. TBD 는 결정 부재.

해결:
- 진짜 결정 못했으면 Open Question 섹션에 명시 + 차단 조건 명시
- 임시값이라도 정하고 "튜닝 가능" 으로 표시

---

### A3. 이름·용어 흔들림

```
❌ 같은 시스템을 한 GDD 에서 "스포너", "오브젝트 매니저", "Spawner" 혼용
✅ 정식 명칭 1개 사용. 약어는 한 번 정의 후 일관 사용
```

문제: 검색·참조·자동화 도구가 작동 안 함.

해결: 첫 등장 시 정식명 정의. 시스템 인덱스의 이름과 일치.

---

### A4. 마케팅 카피화

```
❌ "혁신적인 메카닉으로 플레이어에게 잊을 수 없는 경험을 선사"
✅ "오브젝트 6개 동시 표시 + 0.7초 평균 수명. 즉각 결단 메카닉의 인지 부하 한계 검증."
```

문제: GDD 는 디자이너용 작업 문서. 마케팅 톤은 검토 노이즈.

해결: 누구를 위해 쓰는지 자각. 디자이너·프로그래머가 *작동 방식*을 알 수 있게.

## 섹션별 안티패턴

### Overview (1번 섹션)

#### O1. 다른 섹션 침범
```
❌ Overview 에 "공식: Score = Base × Combo..." 가 들어옴
✅ Overview 는 한 문단 요약. 공식은 4번 섹션.
```

#### O2. 시스템 vs 기능 혼란
```
❌ "이 시스템은 점수 표시, 캐치 처리, 콤보 계산을 담당함" — 3개 시스템이 합쳐짐
✅ 단일 책임 1개. 다른 책임은 별 시스템으로 분리
```

#### O3. 입출력 누락
```
❌ "이 시스템은 미니게임을 제공함" — 무엇을 받고 무엇을 내보내는지 없음
✅ "입력: 사용자 클릭 → 출력: 캐치 이벤트, 점수, 콤보 갱신"
```

---

### Player Fantasy (2번 섹션)

#### F1. 메카닉 무관 감정
```
❌ "비장한 분위기를 느낀다" — 어떤 메카닉으로?
✅ "오브젝트 99% 가 사라진 후 남은 1초에 LEGENDARY 등장 = 마지막 기회 → 비장함"
```

#### F2. 일반론
```
❌ "재미있고 만족스러움"
✅ "0.5초 내 6개 중 3개를 잡아낸 순간의 인지 정점 + 즉각 점수 피드백 = 쾌감"
```

#### F3. 시스템 작동 묘사
```
❌ Player Fantasy 에 룰 설명이 들어옴
✅ Fantasy 는 *느낌*만. 룰은 3번 섹션.
```

---

### Detailed Rules (3번 섹션)

#### R1. 모호한 수식어
```
❌ "적절한 시점에", "일반적으로", "보통", "필요 시"
✅ 정확한 트리거: "콤보 ≥ 5 일 때", "오브젝트 수명 < 200ms 일 때"
```

#### R2. 룰 우선순위 누락
```
❌ "R-1: A 일 때 X. R-2: B 일 때 Y." — A 와 B 가 동시에 참이면?
✅ "R-1 우선. R-2 는 R-1 미적용 시에만."
```

#### R3. 한 룰에 다중 조건
```
❌ "R-N: 점수가 100 이상이고 콤보가 5 이상이면 보너스, 단 LEGENDARY 캐치 직후가 아니면..."
✅ R-N1, R-N2, R-N3 으로 분리
```

#### R4. 룰 수 부족
```
❌ Detailed Rules 가 룰 2개 — 시스템이 너무 단순하거나 룰이 빠진 것
✅ 보통 5~15개. 적으면 누락 가능성 의심
```

---

### Formulas (4번 섹션)

#### M1. 변수 정의 부재
```
❌ "Score = Base × Combo × Bonus"
✅ Base, Combo, Bonus 각각 정의 + 타입 + 범위 + 예시
```

#### M2. 범위 없음
```
❌ "Combo: 0 이상의 정수"
✅ "Combo: [0, 99]. 100 이상은 99 로 캡"
```

#### M3. 예시 없음
```
❌ 복잡한 공식만 적고 예시 없음
✅ 최소 2개 예시 (일반 케이스 + 경계 케이스)
```

#### M4. 단위 없음
```
❌ "spawn_rate: 100"
✅ "spawn_rate: 100ms 마다 1개" 또는 "spawn_rate: 10/초"
```

---

### Edge Cases (5번 섹션)

#### E1. "적절히 처리"
```
❌ "예외 발생 시 적절히 처리"
✅ "예외 시 미니게임 일시정지 + 사용자에게 modal '오류 발생' + 메인 메뉴 복귀"
```

#### E2. 케이스 수 부족
```
❌ Edge Cases 0~2개
✅ 최소 5개. 일반적 시스템은 7~10개
```

#### E3. 사용자 피드백 누락
```
❌ "타임아웃 시 시스템 종료"
✅ "타임아웃 시 시스템 종료. 사용자에게 '시간 초과' 메시지 1초 표시 후 결과 화면 전환"
```

#### E4. "가능한 케이스" 만 적기
```
❌ "정상 플레이 중 발생할 만한 것"
✅ 비정상 입력 (alt+tab, network drop, save corruption) 도 명시
```

---

### Dependencies (6번 섹션)

#### D1. 한 줄로만
```
❌ "스코어링과 연결됨"
✅ 인터페이스 이름 + 사용 패턴 + 결합 강도 (양방향 검증)
```

#### D2. 양방향 누락
```
❌ A → B 로만 적고 B 의 GDD 에 A 가 없음
✅ 양쪽 모두 명시. cross-review 시 반드시 검증
```

#### D3. 레이어 위반
```
❌ Foundation 시스템(오브젝트 DB) 이 Feature 시스템(스코어링) 에 의존
✅ 의존 방향 위→아래만. 역방향은 시그널/이벤트로 분리
```

#### D4. 의존 폭주
```
❌ 한 시스템의 상위 의존 7개 이상
✅ 단일 책임 위반 신호. 시스템 분해 검토
```

---

### Tuning Knobs (7번 섹션)

#### T1. 범위 없음
```
❌ "spawn_interval_ms: 700 (조정 가능)"
✅ "spawn_interval_ms: 700, 안전 범위 [200, 1500]"
```

#### T2. 영향 누락
```
❌ "max_active_objects: 6"
✅ "max_active_objects: 6, 영향: 인지 부하 (높을수록 어려움)"
```

#### T3. 노브 의존성 누락
```
❌ "spawn_interval 과 lifetime 모두 별도 조정 가능"
✅ "spawn_interval ≤ lifetime/2 권장 — 화면 비어 보임 방지"
```

#### T4. 모든 값을 노브로
```
❌ 100개 변수 모두 튜닝 노브로
✅ 디자이너가 *실제로 조정할* 변수만 (보통 5~15개)
```

---

### Acceptance Criteria (8번 섹션)

#### AC1. 측정 불가능
```
❌ "AC: 게임이 재미있어야 함"
✅ "AC: 평균 세션 5분 이상 (3+ 명 플레이테스트)"
```

#### AC2. 환경 미명시
```
❌ "AC: 60fps 유지"
✅ "AC: M1 Mac 기본 사양에서 1080p 60fps 유지, 동시 활성 오브젝트 6개 기준"
```

#### AC3. 주관적 평가
```
❌ "AC: 컨트롤이 자연스러움"
✅ "AC: 클릭 → 시각 피드백 < 100ms (3 frames @ 60fps)"
```

#### AC4. 통과 조건 모호
```
❌ "AC: 메모리 사용량이 적당해야 함"
✅ "AC: 5분 플레이 후 메모리 증가 < 5MB (시작 시점 대비)"
```

## 메타 안티패턴 (구조)

### S1. 살아있지 않은 GDD (Living Document 위반)

증상: GDD 가 작성 후 6개월 동안 수정되지 않음. 코드는 진화했으나 GDD 는 stale.

해결: GDD 에 `last_updated` 필드 + 매주 1회 검토. `/propagate-design-change` 로 코드 변경의 GDD 영향 추적.

---

### S2. 기둥 부재

증상: GDD 가 어느 게임 기둥을 강화하는지 명시 안 됨.

해결: 모든 시스템 GDD 의 첫머리에 "기둥 정렬" 1줄 명시. 기둥과 무관한 시스템 = 스코프 외.

---

### S3. 8섹션 미준수

증상: GDD 에 섹션 누락 (Edge Cases 빠지거나, Formulas 가 없거나).

해결: `/design-review` 또는 동등한 검증으로 차단. 누락 = NEEDS REVISION.

---

### S4. 시스템 인덱스 미반영

증상: GDD 작성됐지만 systems-index.md 의 상태가 갱신 안 됨.

해결: GDD 변경 시 systems-index.md 동시 수정. 자동화 (script) 권장.

---

## 안티패턴 검증 체크리스트

GDD 작성 후 체크 (또는 cross-review 시):

- [ ] 정성 단어 없음 (재미있는, 독특한 등)
- [ ] TBD/미정 없음 (또는 Open Question 으로 명시)
- [ ] 용어 일관됨
- [ ] 마케팅 카피 없음
- [ ] 8섹션 모두 단일 책임 (다른 섹션 영역 침범 X)
- [ ] 룰에 모호한 수식어 없음
- [ ] 공식의 모든 변수 정의 + 범위 + 예시
- [ ] 엣지 케이스 5개 이상, 각각 명시적 처리
- [ ] 의존성 양방향 일치
- [ ] 튜닝 노브 모두 안전 범위
- [ ] AC 모두 측정 가능 + 환경 명시
- [ ] 기둥 정렬 명시
- [ ] systems-index.md 와 동기화됨
