# 접근성 요구사항

> 접근성 = "더 많은 사람이 게임을 즐길 수 있게". 도덕적 의무이자 시장 확대.
> 한국 인구의 5%, 미국 26% 가 어떤 형태든 장애 — 작은 시장 아님.

## 핵심 원리

접근성은 *기능*이 아니라 *디자인 철학*. 프로젝트 *시작 시점*에 tier 결정 → 모든 디자인 결정에 반영.

4 축으로 분해:
1. **시각** (Visual) — 시력·색맹·빛 민감
2. **운동** (Motor) — 정밀 입력·반응 속도·피로
3. **인지** (Cognitive) — 학습·기억·집중
4. **청각** (Auditory) — 소리·음성·자막

---

## Tier 결정

프로젝트 *시작 시* commit:

| Tier | 정의 | 적용 게임 |
|------|------|-----------|
| **Basic** | 가장 기본 (자막, 키 리매핑) | 모든 게임 의무 |
| **Standard** | 위 + 색맹·텍스트 크기·소리 큐 | 대부분 게임 권장 |
| **Comprehensive** | 위 + 보조 입력·자동 모드·내레이션 | 인디 야심작 |
| **Exemplary** | 위 + 스크린 리더·완전 색맹 모드·인지 보조 | AAA 또는 접근성 특화 |

**선택 기준**:
- 1인 인디: Basic (필수) ~ Standard (가능 시)
- 소규모 팀: Standard (권장) ~ Comprehensive (야심)
- AAA: Exemplary (의무, 일부 시장 법적 요구)

---

## 4 축 × Tier 매트릭스

### Tier: Basic (모든 게임 의무)

| 축 | 요구사항 |
|---|---------|
| 시각 | 텍스트 가독성 (대비 4.5:1 이상), 깜빡임 < 3 Hz |
| 운동 | 키/버튼 리매핑, 마우스 감도 조절, 일시정지 |
| 인지 | 튜토리얼, 명확한 피드백, 진행 저장 |
| 청각 | 자막·음성 명령 자막, BGM/SFX 별도 볼륨 |

### Tier: Standard (대부분 권장)

추가:
| 축 | 요구사항 |
|---|---------|
| 시각 | 텍스트 크기 조절, 색맹 모드 (3 종 - 적·녹·청), 색 외 정보 표시 |
| 운동 | Hold → Toggle 옵션, 입력 윈도우 확대 옵션, 자동 조준 옵션 |
| 인지 | 난이도 옵션, 도움말 토글, 텍스트 속도 조절 |
| 청각 | 시각 음향 신호 (소리 → 화면 인디케이터), 음성 → 자막 |

### Tier: Comprehensive (인디 야심작)

추가:
| 축 | 요구사항 |
|---|---------|
| 시각 | High contrast 모드, 모션 감소 (멀미 방지), UI 스케일 |
| 운동 | One-handed 모드, 어택 자동 반복, 컨트롤러 완전 커스텀 |
| 인지 | "쉬움" 보조 (자동 길찾기·힌트), 시간 제한 해제 옵션 |
| 청각 | 진동·햅틱 보조, 햅틱 → 시각 대체 |

### Tier: Exemplary (AAA 또는 특화)

추가:
| 축 | 요구사항 |
|---|---------|
| 시각 | 스크린 리더 호환, 완전 시각 보조 (소리 기반 게임 가능) |
| 운동 | 입력 보조 장치 호환 (Adaptive Controller 등) |
| 인지 | 게임 속도 조절 (slower than normal), 결정 보조 (선택지 강조) |
| 청각 | ASL/수어 비디오 (해당 시), 진동 패턴 다중화 |

## 디자인 결정 시점

### 컨셉 단계 (단계 1)
- Tier 결정 (commit)
- 핵심 메카닉이 *어떤 축* 의 능력을 요구하는지 식별
  - 정밀 클릭 = 운동
  - 패턴 인식 = 시각·인지
  - 음향 큐 = 청각

### 시스템 설계 단계 (단계 5)
- 각 시스템 GDD 의 "접근성 영향" 섹션
- 어느 능력에 *과도하게* 의존하는지 식별
- 보조 메카닉 또는 옵션 설계

### 통합 명세 단계 (단계 6)
- D. UX 흐름 섹션에 접근성 옵션 명시
- 옵션 화면의 접근성 카테고리 구조

---

## 안티패턴

### 1. 출시 직전에 접근성 추가
"개발 거의 끝났으니 접근성 옵션 좀 넣자" → 핵심 메카닉이 이미 한 능력에 의존 → 해결 불가능.

해결: 컨셉 단계부터 tier commit. 모든 시스템 설계가 접근성 고려.

---

### 2. 한 옵션으로 다 해결 시도
"색맹 모드 1개 만들면 끝" → 적·녹·청 색맹 다 다름. 모션 감소도 별개.

해결: 각 축의 각 요구사항이 *별 옵션*. 묶어서 켜고 끄는 "프리셋" 도 제공.

---

### 3. 접근성 옵션이 게임을 *깨뜨림*
"자동 조준 옵션 켜면 보스가 너무 쉬워짐" → 옵션 사용자가 *제대로* 게임 못 즐김.

해결: 접근성 옵션은 *경험을 동등하게* 만들어야 함. 깨뜨리지 말 것.

---

### 4. "정상 모드 vs 접근성 모드" 분리
접근성 사용자가 *별 모드* 라고 느낌 → 차별감.

해결: 모든 옵션을 일반 옵션과 통합. "접근성" 카테고리만 분리하면 OK.

---

### 5. 한국 접근성 가이드 미인식
한국 게임은 한국 접근성 표준 (e.g. KS X 9000 시리즈, 게임 콘텐츠 접근성 가이드라인) 인지 필요. 글로벌 출시 시 EU EAA, US ADA 등.

해결: 출시 지역별 표준 점검 (콘솔 인증 필수 항목 포함).

## 검증 체크리스트

- [ ] Tier commit (Basic/Standard/Comprehensive/Exemplary)
- [ ] 4 축 모두 tier 별 요구사항 명시
- [ ] 핵심 메카닉이 어느 축에 *과도 의존*하는지 식별
- [ ] 의존 축마다 보조 메카닉 또는 옵션 설계
- [ ] 옵션 화면의 접근성 카테고리 구조 명시
- [ ] 접근성 옵션 활성 시 *동등한* 경험 (게임 안 깨짐)
- [ ] 출시 지역별 법적·인증 요구사항 점검
- [ ] 플레이테스트에 접근성 사용자 포함 (가능 시)
