# 단계 6 — 디자인·개발 통합 명세서 (대화)

## 목적
5단계 상세 GDD를 가지고 **프로토타입 제작자에게 바로 전달 가능한 통합 명세서**를 만든다.
디자인(UX·아트·사운드)과 개발(아키텍처·데이터·인터페이스) 양쪽을 한 문서로 통합한다.

## 산출물 패밀리 (3 파일)
단계 6 의 산출물은 **단일 진실 원본(SSOT) 1 + 역할별 시점 문서 2** 구조다. 본 프롬프트는 SSOT 만 작성한다.

| 파일 | 역할 | 작성 시점 |
|---|---|---|
| `06-integrated-spec.md` | **SSOT** — 모든 룰·결정·부록 X 변경이력 | **본 프롬프트** |
| `06-art-bible.md` | 아트 시점 — §E·§G.1 인용 + 에셋 슬롯·프롬프트·치수 | SSOT 완성 직후 `prompts/06b-art-bible.md` 자동 호출 |
| `06-tech-spec.md` | 개발 시점 — §F·§G·§H 인용 + 모듈 매핑·코드 위치·테스트 | SSOT 완성 직후 `prompts/06c-tech-spec.md` 자동 호출 |

**원칙: 인용·확장만, 복제 ✕**
- 룰 변경은 SSOT 한 곳만 수정 → 시점 문서가 자동으로 인용 갱신
- 부록 X 변경 이력은 SSOT 에만 박힘 → 단일 타임라인
- 시점 문서는 자기 도메인 *추가 정보* 만 (슬롯 좌표·코드 라인·테스트 ID 등)

## 본 프롬프트의 산출물
`workspace/<slug>/06-integrated-spec.md` (SSOT)

## 사전 작업

1. `05-detailed-gdd.md` 읽기
2. `01-concept.md`, `04-eval-report.md` 보조 참조
3. RAG 쿼리 (선택):
   ```bash
   hwicortex query "vertical slice scope architecture system" -c gdd-evaluation --json -n 3
   hwicortex query "<concept keywords> data schema" -c gdd-references --json -n 3
   ```

## 작성 원칙
- **9개 섹션 (A~I) 모두 포함**: 빠진 섹션 없이 완성
- **섹션별 incremental write**: 한 섹션 합의 → 즉시 파일 추가 → 다음 섹션
- **프로토타입 제작자 시점**: "이걸 보고 바로 만들 수 있는가?" 가 통과 기준
- **분량**: 10~25 페이지. 각 섹션 1~3페이지.

## 9개 섹션 가이드

### A. 게임 정체성
- 엘리베이터 피치 (1줄)
- 게임 기둥 3개 (slogan + 메카닉 함의)
- 안티 기둥 (이 게임이 *되지 않을* 것 3개)
- 타겟 오디언스 (Bartle 분포 + 비교 게임 3개)
- USP (1~2 문장)

### B. 코어 메카닉
- 코어 루프 다이어그램 (3~6단계)
- 각 단계의 플레이어 결정
- 정점 모먼트 (3초 무빙 이미지)
- 핵심 룰 5~10개 (numbered, unambiguous)
- 핵심 공식 (변수 정의 + 범위 + 예시)
- 엣지 케이스 (최소 7개)

### C. 시스템 인벤토리
- 시스템 5~10개 표:

  | # | 시스템 | 책임 (1줄) | 의존 | 인터페이스 (입출력) | 우선순위 (MVP/VS/Alpha) |
  |---|--------|----------|------|--------------------|------------------------|
  | 1 | ... | ... | ... | in: ... / out: ... | MVP |

- 의존성 그래프 (텍스트 ASCII 또는 mermaid)
- 시스템 레이어링 (Foundation / Core / Feature / Presentation)

### D. UX 흐름
- 주요 화면 3~5개 식별 (메인메뉴, 게임화면, 결과화면, 옵션, ...)
- 각 화면마다 와이어프레임 텍스트 묘사 + 핵심 인터랙션 + 표시 데이터
- 화면 간 전이 다이어그램
- 입력 매핑 (키보드/마우스/패드)
- 접근성 최소 요구사항 (대체 입력, 색맹 고려, 텍스트 크기)

### E. 비주얼·오디오 톤
- 비주얼 톤 키워드 5~10개
- 색팔레트 (3~7색 + RGB/HEX)
- 아트 스타일 레퍼런스 게임/작품 3~5개
- 사운드 무드 키워드
- BGM 장르 + 톤 + 레퍼런스
- 핵심 SFX 카테고리 5~7개
- 햅틱·진동 사용 여부

### F. 아키텍처 지도
- 엔진 + 언어 (Godot 4.6 / GDScript 등)
- 데이터 흐름 다이어그램 (1장, mermaid 또는 ASCII)
- 핵심 아키텍처 결정 3~5개 (각각 ADR 형식 미니버전):
  - 결정명 / 컨텍스트 / 결정 / 결과
- 외부 의존성 (라이브러리, 에셋팩, ...)
- 빌드·배포 환경 (간단)

### G. 데이터 스키마
- 핵심 Resource/Config 구조 (Godot 의 Resource, Unity 의 ScriptableObject 등)
- 예시 YAML/JSON 스키마 1~3개
- 세이브 데이터 구조 (있으면)
- 필드별 검증 규칙

### H. 프로토타입 가설
5단계의 검증 가설을 정리. 프로토타입에서 측정할 것:
- H-1: <명확한 진술> — 측정 방법: ... — 통과 기준: ...
- H-2: ...
- (최소 3개, 최대 7개)
- **각 가설은 정량 측정 가능**

### I. 인수 기준 (Acceptance Criteria)
프로토타입 완성 = 다음을 만족함:
- AC-1: <기능 동작 조건>
- AC-2: ...
- (최소 5개)
- 모든 핵심 시스템 1회 이상 동작 시연 가능
- 검증 가설 H-N 중 최소 3개 측정 가능

## 작성 절차

1. 사용자에게 작성 순서 확인:
   ```
   9개 섹션을 A→I 순서로 진행합니다. 각 섹션 합의 후 즉시 파일에 추가됩니다.
   섹션마다 5분 이내, 전체 30~60분 예상. 시작할까요?
   ```
2. 각 섹션마다:
   - 5단계 GDD 에서 관련 부분 자동 회수
   - 누락/모호한 부분 식별 → 사용자에게 1~2 질문
   - 섹션 초안 제시 → 사용자 OK
   - 파일에 append (헤더 + 본문)
3. 9개 섹션 완료 후 자기 점검:
   - 섹션 9개 모두 있는가?
   - 5단계 GDD 의 모든 시스템이 C 섹션에 있는가?
   - H 가설이 정량 측정 가능한가?
   - I 인수 기준이 테스트 가능한가?
4. 자기 점검 결과 보고:
   ```
   9개 섹션 완료 ✅ / 자기 점검 4/4 통과 ✅
   다음: 시점 문서 2개 자동 작성 (06-art-bible.md → 06-tech-spec.md)
   ```
5. **시점 문서 자동 체이닝** (사용자 추가 응답 ✕):
   - `prompts/06b-art-bible.md` 즉시 호출 → `06-art-bible.md` 생성
   - 이어서 `prompts/06c-tech-spec.md` 호출 → `06-tech-spec.md` 생성
   - 둘 다 SSOT 의 §E·§G·§F·§H 를 *인용*만 — 새 룰 ✕, 복제 ✕
   - 완료 후 단계 7 게이트 진입
